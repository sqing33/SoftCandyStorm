# 测试指标与上线门禁

## 上线质量目标

游戏可以上线，不等于内容很多。它至少要做到：

- 不崩溃
- 不明显卡顿
- 新手能理解
- 每局有成长
- 多数死亡能被玩家接受
- 至少有几种有效流派
- 内容不会被单一 Build 统治
- Bot 和 replay 无明显破坏性回归

## 技术稳定性门禁

必须通过：

- 编译通过
- 单元测试通过
- headless 仿真通过
- 多 seed 不死锁
- replay 可保存和回放
- 内容 schema 校验通过
- 无 panic
- 无 NaN/Infinity
- 无无限生成实体
- 无内存持续增长

## 性能门禁

目标机器暂定：

- 普通 PC
- Steam Deck 级别设备，后续可测

指标：

- 60 FPS 目标
- 大规模怪潮不低于 45 FPS
- 单局实体上限可控
- 特效数量有上限
- 同屏敌人上限按地图/难度配置

Headless 指标：

- 1000 局快速仿真能在可接受时间完成
- 批量测试不能依赖渲染

## 平衡门禁

首版建议阈值：

### 新手体验

- 低技能 Bot 前 2 分钟死亡率不超过 35%
- 中技能 Bot 前 2 分钟死亡率不超过 15%
- 真人新手第一局应至少能看到 2-3 次升级

### 普通难度

- 中技能 Bot 10 分钟胜率：25%-55%
- 高技能规则 Bot 10 分钟胜率：45%-75%
- IdleBot 10 分钟胜率：0%
- RandomBot 10 分钟胜率：低于 15%

这些阈值不是最终真理，但可以作为强门禁初始值。

### Boss

- 第一个 Boss 击杀率不低于 60%
- 最终 Boss 击杀率不高于 50%，除非是高技能 Bot
- Boss 平均击杀时间不能过长导致局面拖死

### 武器

- 没有单个武器在所有 Bot 中伤害占比长期超过 45%，除非它是明确核心武器且有代价。
- 没有武器选择率长期低于 3%，否则需要增强或重做。
- 进化武器必须明显强于未进化，但不能自动赢。

## 内容门禁

每批新内容必须：

- 通过 schema
- 通过静态预算
- 通过快速 Bot
- 通过至少一个人工 review
- 有美术描述
- 有音效描述
- 有图鉴或短文案

AI 生成或候选池内容进入发布候选前，还必须具备对应人工审查证据：

- 素材候选需要通过 `harness/asset_review/validate_asset_candidate_manual_review.py` 对人工审查记录做完整性校验。
- 剧情 / 图鉴候选需要通过 `harness/story_review/validate_story_codex_manual_review.py` 对人工审校记录做完整性校验。
- 遥测、replay 和本地数据相关能力需要有 `harness/telemetry_privacy/validate_telemetry_privacy_policy.py` 通过的隐私策略、`harness/telemetry_privacy/validate_runtime_privacy_settings_contract.py` 通过的 Runtime 隐私设置契约、`harness/telemetry_privacy/validate_upload_transport_contract.py` 通过的上传传输契约、`tools/validate_save_path_policy.py` 通过的平台路径策略，以及 `harness/telemetry_privacy/validate_manual_privacy_review.py`、`tools/validate_manual_platform_path_review.py` 和 `harness/telemetry_privacy/validate_manual_legal_review.py` 通过的人工审查记录；真实 Runtime 仍必须提供关闭选项、raw replay 单独同意、删除 / 导出本地数据入口、平台路径解析和说明文本。

## Replay 回归

每个版本保留代表性 replay：

- 新手死亡局
- 中技能胜利局
- 高技能胜利局
- 经济流
- 防御流
- 控制流
- Boss 流
- 失败 bug 复现局

每次核心数值变化后重放。

比较：

- 死亡时间
- 等级
- 伤害来源
- Boss 时间
- 最大敌人数
- 是否出现新崩溃

## 人工试玩验收

每个可发布候选至少人工玩：

- 3 局新手视角
- 3 局熟练视角
- 3 局不同流派

人工记录：

- 是否看得清
- 是否知道为什么死
- 是否有再来一局冲动
- 升级选择是否有纠结
- 武器反馈是否爽
- 怪潮是否压迫但不烦

当前仓库提供 `harness/playtest/create_manual_playtest_review_draft.py` 从 9 局最小覆盖矩阵生成人工试玩审查草稿，示例草稿位于 `harness/playtest/drafts/2026-05-26_runtime_manual_playtest_review_draft.json`。草稿默认 `needs_more_runs`，并保留 `TODO` 评分，不能作为通过证据。

当前仓库提供 `harness/playtest/create_manual_playtest_review_packet.py` 将 9 局矩阵、必看观察项、TODO 草稿状态、评分字段、允许标签和门禁标签汇总成人工试玩审查包，示例报告位于 `harness/reports/2026-05-26_runtime_manual_playtest_review_packet_001/summary.md`。审查包只帮助真人防漏项，不运行 Runtime、不填写评分、不接受候选，也不替代严格验收校验。

当前仓库提供 `harness/playtest/validate_manual_review.py` 作为人工试玩记录完整性检查工具。它不会替代人工判断，但会拒绝空评分、少于 9 局、非法门禁、缺少具体观察或缺少后续行动的记录；候选内容进入 `accepted_content` 前应使用 `--strict-acceptance` 生成 JSON/Markdown 校验报告。

## 可观测性

局内记录：

- fps
- 实体数量
- 敌人数
- 投射物数量
- 特效数量
- 受伤事件
- 升级选择
- 武器伤害
- Boss 阶段

正式上线前如果接遥测，要注意：

- 默认匿名
- 不记录敏感信息
- 提供关闭选项
- 明确隐私说明

## Release Candidate 流程

1. 冻结内容。
2. 跑全量测试。
3. 跑多 Bot 仿真。
4. 跑 replay 回归。
5. 人工试玩。
6. 修 P0/P1 问题。
7. 只允许低风险调数值。
8. 再跑关键测试。
9. 打包发布候选。

当前仓库提供 `tools/validate_release_candidate_evidence.py` 作为 Release Candidate 证据清单校验器。它不会运行编译、Harness、Replay、性能或人工试玩，只检查每个 release gate 是否有明确、非合成、路径存在的证据。

推荐流程：

```bash
python3 tools/validate_release_candidate_evidence.py \
  harness/release/<candidate_evidence>.json \
  --repo-root . \
  --report harness/reports/<rc_report>/release_candidate_evidence.json \
  --markdown harness/reports/<rc_report>/summary.md
```

只有所有必需 gate 都是 `pass`，且证据路径存在、未标记为 `synthetic` 时，报告才会输出 `release_candidate_ready`。历史 smoke、合成人工审查和候选池预检不能替代真实 release gate。

发布包本身还必须有独立清单，记录 Runtime 包、发布压缩包、校验和、发布说明、内容 lockfile、素材 manifest 和最终 smoke 证据。当前校验器为：

```bash
python3 tools/validate_release_package_manifest.py \
  harness/release/<package_manifest>.json \
  --repo-root . \
  --report harness/reports/<package_report>/release_package_manifest.json \
  --markdown harness/reports/<package_report>/summary.md
```

`release_package_ready` 只说明发布包清单结构和证据完整，不会替代 Release Candidate 全部门禁。当前本地清单 `harness/release/current_local_package_manifest.json` 明确为 `blocked`，在二进制启动、RC 门禁和 final smoke 恢复前不能用于发布。

长时间 Goal 模式下，还应额外运行总账一致性校验：

```bash
python3 tools/validate_goal_evidence_consistency.py \
  --repo-root . \
  --report harness/reports/<goal_consistency_report>/goal_evidence_consistency.json \
  --markdown harness/reports/<goal_consistency_report>/summary.md
```

该校验用于防止 docs 覆盖账本、路线图审计、progress、RC evidence 和 release package manifest 互相矛盾。它不会运行编译、Harness、Replay、性能或人工试玩；即使输出 `goal_evidence_consistent`，只要 RC 仍是 `release_candidate_not_ready` 或发布包仍是 `blocked`，就不能进入发布。
