# 美术与音频素材计划

## 视觉目标

整体风格：可爱、圆润、明亮、糖果质感，但战斗信息必须清楚。

关键词：

- 软糖
- 果冻
- 糖晶
- 泡泡
- 棉花糖
- 焦糖
- 彩虹
- 圆形轮廓
- 高对比边缘
- 小尺寸可读

## 视觉原则

### 1. 形状优先于细节

游戏内敌人数量很多，小尺寸下不能依赖复杂细节。每种敌人必须有明显轮廓：

- 蹦蹦软糖：圆
- 酸酸软糖：尖角/酸粒
- 熊糖：小熊耳朵
- 饼干怪：方圆厚块
- 泡泡：透明圆
- 焦糖怪：拖尾黏液

### 2. 颜色区分行为

颜色要服务玩法：

- 绿色/粉色：普通
- 黄色：快速或酸味
- 蓝色：泡泡/分裂
- 棕色：焦糖/减速
- 红色：危险/冲刺
- 紫色：Boss/特殊

### 3. 可爱但危险信号清楚

危险攻击要有预警：

- 红色地面圈
- 蓄力线
- 闪烁边缘
- 音效提示
- Boss 表情变化

## 素材规格建议

### 分辨率

首版可采用：

- 角色：64x64
- 普通敌人：48x48 或 64x64
- Boss：128x128 或 192x192
- 投射物：32x32
- 掉落物：24x24
- UI 图标：64x64

### 风格

建议使用高清 2D 卡通而非像素风。原因：

- AI 生图更容易得到稳定结果。
- 缩小后仍然可读。
- 后续可以切成 spritesheet。

但动画可以保持简单：

- idle squash/stretch
- 移动弹跳
- 受击闪白
- 死亡弹开/溶解

## AI 生图策略

### 生成方式

优先生成大图 spritesheet，再裁切。

优点：

- 风格统一
- 一次产出多个素材
- 适合快速建立可玩版本

缺点：

- 单格边界可能不干净
- 需要裁切和透明处理
- 角色动作帧一致性需要后续迭代

### 推荐提示词方向

主题：

```text
cute top-down candy roguelite game spritesheet, soft gummy candy world, rounded shapes, high contrast outline, readable at small size, no text, transparent or flat chroma background
```

约束：

```text
each sprite isolated in its own grid cell, centered, generous padding, no shadows crossing cells, no labels, no text, consistent lighting, consistent cute cartoon style
```

### 透明背景

如果工具不能直接透明：

1. 使用纯色 chroma-key 背景。
2. 本地抠图。
3. 输出 PNG。
4. 人工或脚本检查边缘残留。

## UI 风格

UI 要像糖果包装，但不能影响读数。

### HUD

- 左上：生命、等级、时间、击杀
- 下方或右侧：当前武器和被动
- 升级时：三张糖果卡牌
- Boss：顶部血条，带 Boss 名字和小头像

### 升级卡牌

- 图标
- 名称
- 等级
- 效果描述

- 稀有度边框

- 普通：奶白
- 稀有：蓝莓蓝
- 史诗：葡萄紫

## 音频风格

### 音乐

整体：

- 轻快
- 甜点幻想
- 电子 + 木琴 + 铃铛 + 轻鼓点

每张地图有主题变体：

- 糖霜草地：明亮木琴

### 音效

### mmx 生成前计划门禁

后续使用 `mmx` 生图、TTS 或 music 前，应先写生成计划并校验：

```text
harness/asset_review/mmx_asset_generation_plan_template.json
harness/asset_review/validate_mmx_asset_generation_plan.py
```

推荐命令：

```bash
python3 harness/asset_review/validate_mmx_asset_generation_plan.py \
  harness/asset_review/mmx_asset_generation_plan_template.json \
  --repo-root . \
  --report harness/reports/<report-id>/mmx_asset_generation_plan.json \
  --markdown harness/reports/<report-id>/summary.md
```

该计划门禁只检查生成前纪律：输出必须落在 `asset/generated_candidates/<batch>/`，每个 `mmx` 命令必须保留 `--output json --non-interactive --quiet`，不得内联 API key，不得声明 `accepted_content`、`runtime_integrated` 或 `release_ready`，并且必须列出 metadata 校验和人工审查草稿生成步骤。报告结论为 `mmx_asset_generation_plan_valid` 只代表可以进入实际生成尝试，不代表素材存在、可用或通过人工审查。

### 人工审查门禁

素材候选进入 Runtime/UI 接入候选前，必须有人工审查记录。模板与校验器位于：

```text
harness/asset_review/validate_mmx_asset_generation_plan.py
harness/asset_review/asset_candidate_manual_review_template.json
harness/asset_review/create_asset_candidate_review_draft.py
harness/asset_review/create_asset_review_packet.py
harness/asset_review/validate_asset_candidate_manual_review.py
harness/asset_review/promote_asset_runtime_candidate.py
harness/asset_review/validate_asset_runtime_candidate_manifest.py
harness/asset_review/asset_runtime_preview_review_template.json
harness/asset_review/validate_asset_runtime_preview_review.py
harness/asset_review/asset_audio_loudness_review_template.json
harness/asset_review/validate_asset_audio_loudness_review.py
harness/asset_review/asset_final_acceptance_template.json
harness/asset_review/validate_asset_final_acceptance.py
harness/asset_review/create_asset_acceptance_review_packet.py
harness/asset_review/validate_asset_acceptance_manifest.py
harness/asset_review/asset_acceptance_manifest_template.json
```

已有 `mmx` 批次可以先生成审查草稿，确保 manifest 中每个素材 id 都进入人工审查清单：

```bash
python3 harness/asset_review/create_asset_candidate_review_draft.py \
  asset/generated_candidates/<batch> \
  --repo-root . \
  --metadata-report harness/reports/<asset-validation-report>/summary.md \
  --out harness/asset_review/drafts/<batch>_review_draft.json
```

审查草稿只用于防漏项，里面的 `TODO`、占位评分和 `needs_more_review` 不能作为人工通过证据；真人必须填写具体观察、评分、修改项和最终 gate 决策后，才能运行人工审查校验器。若人工审查结论为 `asset_candidate`，可以用 `harness/asset_review/promote_asset_runtime_candidate.py` 复制到 `harness/asset_review/runtime_candidates/`，但该目录仍只是 Runtime/UI 接入候选，不等于正式素材、`accepted_content` 或 Runtime 集成。晋级后还必须校验 `runtime_candidate_manifest.json`，确保它仍声明 `accepted_content=false`、`runtime_integrated=false`、`release_ready=false`，并继续引用源候选 manifest、metadata 报告和人工审查记录。

Runtime 的 `--asset-runtime-candidate-manifest` 只允许读取上述 `runtime_candidate_manifest.json` 的安全元数据，用于在 `F1` 概览提示“素材 Runtime 候选”批次、素材数量和类型统计。它必须拒绝 `accepted_content=true`、`runtime_integrated=true`、`release_ready=true`，以及缺少 Runtime preview、音频响度审查或最终人工接受要求的 manifest；它不会读取候选图片 / 音频文件，也不会替换正式 Runtime 素材。

Runtime 候选进入最终接受前，必须把三类人工证据拆开校验：

- `validate_asset_runtime_preview_review.py`：检查 Runtime preview review 是否绑定有效 Runtime 候选 manifest，并确认可见 / 可听、小尺寸可读、无占位泄漏、无 Runtime 集成声明。
- `validate_asset_audio_loudness_review.py`：检查音频响度 / 听感记录是否绑定有效 Runtime 候选 manifest，并确认语音清晰、响度通过、无削波、循环或时长适配。
- `validate_asset_final_acceptance.py`：检查最终人工接受是否绑定已通过的 Runtime preview review 和 audio loudness review，并保持 `runtime_integrated=false`、`release_ready=false`。

这些模板当前都应保持 invalid；它们是给真人补齐证据的门禁，不会读取或复制素材，也不会把候选变成 Runtime 集成素材。

最终素材接受必须再通过 `harness/asset_review/validate_asset_acceptance_manifest.py`。该 manifest 必须绑定有效 Runtime candidate manifest、Runtime preview review、音频响度 / 听感审查和 final human acceptance，并要求 `accepted_content=true`、`runtime_integrated=false`、`release_ready=false`、`generated_candidate_direct_acceptance_allowed=false`。因此它只记录“素材内容被人工接受”，不代表 Runtime 已加载这些文件，也不代表发布包 ready。

在填写最终接受 manifest 前，可以用 `harness/asset_review/create_asset_acceptance_review_packet.py` 生成最终接受审查包，集中列出 Runtime 候选 manifest、Runtime preview review、音频响度 / 听感审查和 final human acceptance 四类证据的状态。审查包只用于帮助真人补齐证据，不会验证通过、不复制素材、不接入 Runtime、不批准发布。

可以用 `harness/asset_review/create_asset_review_packet.py` 生成 Markdown 审查包，把每个素材 id、候选文件、预览、音频、QA 状态和草稿 TODO 集中起来，便于真人逐项审查。审查包不会替代人工评分，也不会让素材晋级。

审查记录必须覆盖候选批次 manifest 中的每个素材 id，并检查：

- 糖果风格一致性。
- 玩法可读性和小尺寸可读性。
- 透明边缘、裁切、背景残留或音频响度 / 长度问题。
- prompt、source、postprocess 和命令 provenance 是否足够。
- 允许用途是否仍停留在候选范围，不能直接标记为正式 Runtime 素材。
